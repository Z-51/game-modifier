## 0. 先把定位说清楚

在讲任何技术细节之前，必须先讲边界：

> **game-modifier 仅限单机 / 离线游戏的内存修改。** 它在附加进程时会主动
> 检测已知反作弊系统，一旦命中即拒绝附加并终止（错误码 `E_ANTI_CHEAT`，
> 契约是"停止，不要重试"）。它**不提供、也不打算提供**任何反作弊绕过能力，
> 不支持联机作弊，不对抗 DRM，不做代码注入与 hook。

"有所不为"不是这篇分享的附带声明，而是项目排名第一的架构决策（见 §2 与
故事线 D6）。本文聚焦的是架构决策与 AI 协作技术本身。

## 1. 引言：给 AI 用的工具长什么样

多数命令行工具是给**人**设计的：彩色输出、交互式向导、需要阅读理解的错误
提示。这个项目的用户是另一类消费者——编码 Agent（Claude Code、Codex CLI
一类的 AI 编程工具）。Agent 的"注意力"按 token 计费，它不会读长文，只会
解析结构化输出并据此分支。

于是整个设计围绕一个问题展开：**如何让一个 AI 用最少的 token、最少的往返、
最少的推理，安全地完成"找到游戏里的金币地址并把它改掉"这件事？**

答案是四件事：

1. **会话复用**——`attach` 一次拿到 session_id，之后所有调用只带这个 id，
   不再重传进程与模块映射；
2. **符号表**——Agent 引用 `player.gold` 而不是原始指针链；
3. **确定性中文 NLP**——一句"将金币设为9999"直接映射到操作，零 LLM 调用、
   零随机性；
4. **结构化 JSON 信封**——每条命令输出一行 JSON，带稳定错误码，Agent 可以
   像写 switch-case 一样分支，而不是解析自然语言。

下面的故事线，讲的是这些答案背后的取舍。

## 2. 项目速览

**做什么**：Windows 单机游戏的内存读写工具，双入口——CLI（每条命令一行
JSON）与 MCP server（结构化工具调用）。能力覆盖：值扫描与增量收敛、字节
模式（AOB）扫描、指针链/结构体字段链解析、内存布局启发式分析、指针反查、
UE/Unity 引擎内省、数值冻结、存档文件编辑（RPG Maker 等）、模板与批处理。

**不做什么**（安全契约）：

- 检测到反作弊 → 拒绝附加，不提供绕过；
- 写入默认 **dry-run**，必须显式 `--confirm` 才落内存，落前自动备份原值；
- 单次写入有字节上限（默认 4096 字节），超限拒绝；
- 每次确认写入追加审计日志（JSONL），可回溯"AI 改了什么"；
- 不做代码注入、不做 hook、不对抗 DRM。

**关键数字**（截至 2026-08-14 实测）：

| 指标 | 数值 |
| --- | --- |
| 测试用例 | 83 → 290 → 408 → 687 → **858**（9 轮迭代只增不减，零回归） |
| MCP 工具 | 24 → **83**（11 组） |
| 稳定错误码 | **40**（一经发布永不改字面值） |
| 安全 profile | **5 档**（default / limited / symbols / dry-run / readonly） |
| 可选依赖组 | **8 组**（radare2 / frida / mcp / speed / disasm / crypto / dev / all） |
| 反作弊签名 | **16 种**（宁窄勿宽，防误伤单机游戏） |

## 3. 核心设计决策故事线

完整的 32 项决策见 §4 速查表（编号 D1–D32）；这里挑 11 个最有故事性的展开，
小节标题后标注其在速查表中的编号。

### D1 · CLI + MCP 双模式：AI Agent 集成的两条腿

为什么不只做 MCP？因为不是所有 Agent 框架都支持 MCP，但几乎所有能执行
shell 命令的 Agent 都能用 CLI。反过来，MCP 的结构化参数校验与常驻进程
又优于每次冷启动 CLI。

决策是：**两条腿都保留，但共用一个身体**。CLI 与 MCP server 都是同一个
`ModifierService` 的薄壳，任何新功能必须先落在服务层，再同步暴露到两个
壳——否则两条路径的行为会漂移。这条"先服务层、后双壳"的纪律后来成为
PR 检查清单的固定项。

### D2 + D4 · JSON 信封 + 稳定错误码：为 AI 消费者设计的接口

每条命令的输出都是同一个信封：

```json
{"ok": true,  "command": "modify", "data": {...}, "warnings": [...]}
{"ok": false, "command": "modify", "error": {"code": "E_...", "message": "...", "hint": "..."}}
```

两个契约支撑它：

- **错误码是字符串常量且永不修改**。Agent 依赖 `E_NEEDS_SCAN` → 去扫描、
  `E_PROCESS_EXITED` → 重新 attach 这样的固定分支。改一个字面值，等于
  破坏所有下游 Agent 的"编译期契约"。新增错误只能追加（目前 40 个）。
- **错误带 hint**。后期迭代给关键错误码加了可执行的下一步指引（如
  `E_SCAN_TIMEOUT` 直接指向"用 `pointer-scan --async` 后台执行"），让
  Agent 拿到错误即知道下一步，不必推理。

### D5 · dry-run 默认：安全如何成为默认值而非选项

写内存是破坏性操作，而调用者是会犯错的 AI。项目的选择是**把安全做成
默认状态**：`modify` 不加 `--confirm` 时永远是 dry-run——校验、解析、
读旧值都照常执行，还附带一份 `impact` 预览（目标区域、新旧值、将创建的
备份），唯独不写。

这不是"防呆开关"，而是交互设计：Agent 的第一次调用天然是试探，dry-run
让试探本身变成有价值的信息获取。忘了加 confirm？返回 `E_NOT_CONFIRMED`，
信息性提示，不是灾难。

### D3 · 会话复用：token 效率的第一杠杆

游戏进程的模块列表动辄几十条，指针链解析的中间步骤更是冗长。如果每次
调用都重传这些上下文，token 消耗会淹没真正的意图。`attach` 一次把进程
身份、模块基址、符号表、扫描状态全部持久化进 session 文件，之后所有调用
只传一个 session_id——这是全项目性价比最高的单项决策。

### D6 · 反作弊拒绝边界：有所不为的设计

附加流程里有一道硬闸门：对目标进程的模块名与共存进程名做签名匹配，
命中 16 种已知反作弊系统之一（EasyAntiCheat、BattlEye、TenSafe 等）即
拒绝附加并终止。

两个细节值得讲：

- **签名刻意收窄**。例如绝不匹配 "steamclient" 或 "valve" 这类宽泛子串——
  那会让所有 Steam 单机游戏被误杀；只匹配明确的 VAC 执行模块。宁可漏
  报（保守场景由用户自觉），不可误伤。
- **拒绝是终态**。错误契约写明 `E_ANTI_CHEAT` 的唯一正确动作是"停止"，
  连重试都不建议。工具不提供任何削弱该闸门的配置路径给自动化流程。

### D11 · confidence + evidence：启发式分析的诚实表达

内存布局分析（vtable 重建、RTTI 类名、堆对象枚举、UE 结构探测）本质是
启发式——结论可能对，也可能错。让 AI 拿着一个"可能错"的结论去写内存，
是灾难配方。

项目的做法是把不确定性显式化：所有分析结果强制携带 `confidence`
（0.0–0.95）与 `reason` / `evidence` 字段（例如"N/M 条目具指针形状"）。
探测失败甚至不抛异常——返回 `verdict: failed` 加每个候选的证据，把判断权
交还给 Agent。配套约束：布局分析结果不直接接 modify，必须经人工
`name set` 固化为符号后才可写。这是"诚实的启发式"原则的完整落地。

### D13 · 邻近归组批读：一次性能优化的完整推理链

UE 内省要枚举最多 50,000 个对象，逐个读 ClassPrivate 与 FName 意味着约
60 万次系统调用。优化推理链如下：

1. 第一反应是复用现成的 `read_many` 批量读——**被否决**：它的实现是
   per-address 先查内存区域属性，数万地址下这个查询本身就是灾难；
2. 自研邻近归组：地址排序 → 间隔小于阈值（默认 256 字节）的归为一组 →
   每组一次读整段再切片 → 整段读失败则退化为组内逐地址读（容错不丢数据）；
3. 叠加三层缓存：唯一类缓存（类链判定共享前缀）、FName 索引去重缓存、
   Actor 判定缓存；
4. 测试用读计数器断言：枚举 N 个对象的读次数必须是 O(chunks+groups)
   而非 O(N)。

最终：60 万次 → 3,000–7,000 次，降 99%。这个故事的价值在于第 2 步——
**现成的"批量"抽象未必适合你的访存形态，性能设计要看底层语义**。

### D28 · field_chain vs pointer_chain：一个实战 bug 催生的语义分离

实战事故：Agent 调用 `modify(address=0x21EF..., offsets=0x4)` 想改结构体
偏移 +4 处的字段，结果报"地址 0x98b0... 不在映射区域内"——一个垃圾地址。

根因：offsets 一直遵循 Cheat Engine 的指针链语义（每级先解引用再加偏移），
这对多级指针是对的，但"结构体基址 + 字段偏移"场景会被错误地解引用——把
基址处的 8 字节**当指针读出来**再加偏移。

修复没有选择"加个参数开关了事"，而是做了语义分层，最终形成三种模式：

- `relative`：基址 + 偏移直接相加（结构体字段）；
- `pointer_chain`：解引用 + 偏移循环（CE 指针链，默认，向后兼容）；
- `field_chain`：加偏移 + 解引用交替（结构体字段链，如
  `gem.__data.MainPowerData.mPowerType`），配 `deref_last` 控制末端。

外加智能默认：纯绝对地址 + offsets 自动走 relative，`模块+偏移` 形式保持
指针链。**一个名字的歧义，用三个显式语义偿还**——这是接口设计债的典型
清偿方式。

### D23 · 多级安全 profile：细粒度权限的演进

只读部署的需求出现后，第一版只做了 `--profile readonly`（写工具不注册）。
但实际场景很快分化：有人想让 AI 能建符号表但不能写内存；有人想允许单点
modify 但禁止批量操作；有人想要"写工具在，但服务端拒绝一切 confirm"。

最终演进为 5 档：`readonly`（53 个只读工具）→ `symbols`（+符号管理/快照）
→ `limited`（+单点 modify/nl）→ `default`（全量 83 个）→ 正交的
`dry-run` 档（工具全注册但 confirm 被服务端拒绝）。另配运行时安全档位
（`safety_set_level` 切到 `dry_run_only` 可动态冻结一切写入）。

教训：**权限模型不要一步设计到位，但要留好正交扩展的维度**——注册面
（哪些工具可见）与执行面（confirm 是否放行）分离，是后来扩展不破坏兼容
的关键。

### D9 · 可选依赖降级：最小内核 + 按需增强

核心依赖只有 psutil、PyYAML 与 tomli 三个。capstone（反汇编）、r2pipe（静态分析）、
numpy（向量化扫描）、mcp 全部是可选项：缺失时相关功能返回带安装指引的
错误码（`E_DEPENDENCY_MISSING` / `E_TOOL_NOT_FOUND` + `install_hint`），
而不是 import 崩溃。平台后端同理——非 Windows 上 `import game_modifier`
依然安全，只有真正调用内存后端才抛 `E_UNSUPPORTED_OS`。

这让工具可以在任何 Agent 环境里"先装上再说"，能力边界由错误码如实汇报。

### 追加式演进（贯穿 D4/D5/D8 等）：8 轮迭代零回归的工程纪律

测试基线 83→290→408→687→858，只增不减。支撑它的是一组追加式约定：错误码
只追加；抽象基类的新方法禁止抽象（用带默认实现的便利方法，保护测试替身
FakeBackend）；持久化结构的新字段带默认值、反序列化容错旧文件；现有
MCP 工具签名与返回结构零改动。

这不是风格偏好，而是多智能体并行开发的前提——没有这条铁律，并行迭代
会把回归风险滚成雪崩。

## 5. AI 多智能体协作开发的方法论收获（精简版）

本项目由 Leader 智能体编排多类专职智能体（调研规划 / 编码实现 / 验证 /
文档收尾 / 评审）完成 8 轮迭代。四个最值得带走的做法：

1. **三视角并行规划**：重大功能先派 3 个调研智能体从简洁性 / 性能 / 最小
   变更三视角独立出方案，综合评审时把否决理由写进计划（Rejected
   Alternatives）——UE 内省功能即用此法融合出最终方案。
2. **锚点隔离并行**：多个编码智能体同改枢纽文件时，任务指令里用"文件 +
   区块锚点"划定写入边界，锚点外只读。
3. **基线验证门**：每阶段收尾全量回归 + wheel 重建核对内容 + CLI 冒烟，
   测试数只增不减。
4. **失败先归属再修复**：并行期间的测试失败先比对失败位置与各智能体的
   锚点范围，确认责任人，避免双重修改冲突。

完整机制、冲突案例与迭代时间线见 03《决策复盘 · AI 协作案例版》。

## 6. 结语：四条设计原则

回头看 32 项决策，它们其实是四条原则的不同投影：

1. **为 AI 消费者设计接口**——输出的第一读者是 Agent，不是人。结构化、
   稳定、可分支，比漂亮更重要。
2. **安全即默认**——dry-run 是默认态，confirm 是显式动作，备份是自动的，
   拒绝边界是终态。安全性不靠使用者记得开开关，而靠默认值。
3. **诚实的启发式**——推测就标注置信度，失败就给出证据，不确定就交还
   决策权。AI 工具最怕的不是能力弱，而是自信地错。
4. **追加式演进**——接口只加不改，基线只增不减，语义混淆时用显式分层
   偿还。演进速度由此不再以回归风险为代价。

最后重申开头那句边界：这套架构服务于**单机与离线游戏**的场景。工具的
克制，正是它能被信任的前提。
