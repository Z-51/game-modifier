## 1. 引言

## 4. 决策详述

### 初始架构层（D1–D10）

#### D1. CLI + MCP 双模式设计

**背景/痛点**：工具的目标用户是编码 Agent。不同 Agent 宿主能力不同：有的只有 shell（只能走 CLI），有的支持 MCP 结构化工具调用。单一形态会把一半用户挡在门外。

**采纳方案**：一份 `service.py` 服务层，上面架两个薄壳——`cli.py`（argparse 子命令）与 `mcp_server.py`（FastMCP 工具注册）。业务逻辑零重复，两种形态行为一致。

**备选与否决理由**：早期决策，计划文件无正式记录。实际演进中验证了该选择：P4 阶段借鉴 ida-pro-mcp 时，其 Rejected Alternative #5 明确否决了"照搬自研 zeromcp/AST 代理生成"——复杂度超出需求，保持 FastMCP + 手写薄包装（项目现有模式），仅吸收其输出限流、置信度、审计等设计思想。这与双模式薄壳 philosophy 一脉相承。

**可复用的设计原则**：**把业务逻辑收敛到一个服务层，让每种接入形态退化为"参数翻译 + 输出包装"的薄壳**。新增接入形态（HTTP、SDK）的成本从此与业务复杂度解耦。

#### D2. JSON 信封统一输出

**背景/痛点**：LLM 解析自由文本极易出错且消耗 token。Agent 需要能"按 code 分支"而不是"读懂 prose"。

**采纳方案**：所有 CLI 命令输出一行 JSON：`{"ok": bool, "command": ..., "data"|"error": ...}`；错误统一为 `{"code": "E_*", "message", "hint?", "details?"}`。MCP 侧由 `_envelope` 包装成同样形状。

**备选与否决理由**：早期决策，无正式记录。对照依据：retrospective 明确指出"紧凑 JSON + 稳定 error.code：可分支而无需解析 prose"是 token 效率的核心手段。人类可读格式作为可选的 `human` 输出模式旁路，不污染机器主路径。

**可复用的设计原则**：**面向机器的接口，输出结构本身就是 API 的一部分——信封形状一旦发布就是契约**。人类友好性用可选视图解决，绝不混入主协议。

#### D3. session 复用模型（token 效率核心）

**背景/痛点**：attach 一个进程需要枚举模块、探测引擎、建立句柄。如果每次 read/modify 都重传进程信息与模块映射表，token 成本爆炸。

**采纳方案**：`attach` 一次生成 `session_id`，进程句柄、模块表、引擎结论、符号表全部持久化在 `sessions/<id>/`；后续所有命令只传 `session_id`。

**备选与否决理由**：早期决策，无正式记录。后续演进持续强化该模型（D21 快照、D29 转储关联、UE 布局缓存都挂在 session 上），证明它是正确的承重墙。

**可复用的设计原则**：**为 LLM 客户端设计工具时，把"昂贵的上下文建立"变成可复用的会话对象**——每节省一次重复传输，都是复利式的 token 节约。

#### D4. 稳定错误码体系（E_* 枚举）

**背景/痛点**：Agent 遇到错误需要确定性恢复路径（扫描失败→先 scan；符号缺失→name set；进程退出→重新 attach）。靠解析错误文本无法可靠分支。

**采纳方案**：`errors.py` 定义 `ErrorCode` 枚举（当前 40 个），每个错误码对应异常子类；**只追加、不改值**。AGENTS.md 写明恢复手册：`E_ANTI_CHEAT`→停止、`E_NEEDS_SCAN`→扫描后 name set、`E_PROCESS_EXITED`→重连等。

**备选与否决理由**：P4 计划文件的"向后兼容铁律"明确："errors.py 仅追加枚举值"。UE 计划 Rejected Alternative #3 更直接：曾考虑新增 `E_UE_LAYOUT_INVALID`，因"语义与现有 LAYOUT_UNSUPPORTED 重叠，复用现有码减少 API 面"被否决——错误码也要克制膨胀。

**可复用的设计原则**：**错误码是给机器的分支条件，其字符串值就是 ABI**；新增优先复用近义码，API 面越小 Agent 越不容易迷路。

#### D5. dry-run 默认 + confirm 门控

**背景/痛点**：Agent 会自主发起写入。写错地址、写错值在游戏内存上不可撤销，必须有"预览→确认"两步。

**采纳方案**：所有写操作（modify/nl/batch/save-edit）默认 dry-run，返回将发生的变更而不执行；必须显式 `--confirm` / `confirm=true` 才真正写入。服务端二次校验，不信任客户端。

**备选与否决理由**：早期决策，无正式记录。后续 D23–D25 层层加固（profile 可服务端拒绝 confirm、运行时档位可整体禁写），说明该门控被视为可叠加的防线而非单点。

**可复用的设计原则**：**任何有副作用的 AI 工具接口，默认态必须是无害的预览；确认必须是显式动作，且服务端永远保留否决权**。

#### D6. 反作弊检测 = 拒绝附加（不绕过）的边界

**背景/痛点**：工具可被滥用于联机/竞技游戏，导致封号与法律风险；写内核级反作弊保护的进程也极易崩溃目标。

**采纳方案**：`safety/guard.py` 维护 16 种反作弊系统的模块/进程名签名（EAC、BattlEye、Vanguard、TenSafe/ACE、NEACProtect 等），attach 时命中即 `E_ANTI_CHEAT` 拒绝，hint 直接告知"停止操作，改用单机或 save-edit"。

**备选与否决理由**：无"绕过"备选——这是项目宪法级边界，AGENTS.md 与 HANDOVER_GUIDE 均声明为硬性安全契约。P4 计划阶段一 1.3 仅做"纯数据追加"扩充签名，刻意保持 `{detected, systems, hits}` 返回结构不变。VAC 签名刻意收窄（只匹配 `vacmodule`，不匹配 steamclient）以防单机 Steam 游戏误伤——边界要硬，但误报要低。

**可复用的设计原则**：**给 AI 工具划伦理/安全边界时，拒绝要早（入口层）、要响（结构化错误码）、要带出路（hint 指明合法替代路径）**。

#### D7. 写入前自动备份 + 审计日志

**背景/痛点**：即使有 dry-run，确认写入后仍可能发现改错了。需要可回滚。

**采纳方案**：每次确认写入自动备份原值（`backup_create/list/restore`）；P4 起所有写操作追加 JSONL 审计流水 `sessions/<id>/audit.jsonl`（`{ts, op, args, result, backup_id}`，`audit_tail` 可读回），与 backup_restore 形成闭环。

**备选与否决理由**：P4 计划"参考项目借鉴"明确审计日志取自 ida-pro-mcp 模式："写操作 JSONL 流水账（与 backup 闭环，支撑 AI 修改回溯）"。被隐含否决的替代是"只靠 git/外部日志"——会话级流水账才能与 session 生命周期对齐。

**可复用的设计原则**：**AI 执行的每个副作用都要留下"可回溯 + 可撤销"的双重凭证**；审计粒度对齐会话，回滚粒度对齐单次写入。

#### D8. FakeBackend 测试架构

**背景/痛点**：内存操作依赖真实进程与管理员权限，CI 里无法跑；但扫描/分析逻辑又必须高覆盖测试。

**采纳方案**：`MemoryBackend` 抽象契约 + `tests/conftest.py` 的 `FakeBackend`（字典式伪内存），测试手工布置字节即可覆盖扫描器、布局分析、UE 内省等全部逻辑。新后端能力一律用**具体默认方法**实现（如 `read_many` 默认逐条 read），严禁 `@abstractmethod`。

**备选与否决理由**：P4 计划风险表第一条即铁律："MemoryBackend 加抽象方法破坏 FakeBackend → 一律用具体默认方法实现，禁止 @abstractmethod"。被否决的替代是"mock 真实 Windows API"——脆弱且无法覆盖语义。UE 计划测试章节进一步要求"批读次数断言"（FakeBackend 加读计数器），证明该夹具还能承担性能契约验证。

**可复用的设计原则**：**把平台能力抽象成小契约接口，用可手工布置的假实现承载全部测试；扩展契约时用默认实现保持旧实现者零改动**——这是接口演进的开闭原则落地。

#### D9. 可选依赖组 + 懒加载降级

**背景/痛点**：numpy/capstone/r2pipe/pycryptodome/mcp 各自有用，但全装会让最小安装臃肿，缺一个就整体不可用更不可接受。

**采纳方案**：`pyproject.toml` 拆 8 组 extras（radare2/frida/mcp/speed/disasm/crypto/dev/all），核心仅 psutil+PyYAML+tomli；所有可选依赖 try-import 懒加载，缺失时降级并返回 `E_DEPENDENCY_MISSING`（带安装命令 hint）。

**备选与否决理由**：P4 计划 Rejected Alternative #3："引入 capstone/keystone 等重依赖——违反最小依赖原则；vtable/RTTI 用结构化启发式实现"。注意后续演进（P6）把 capstone 以 `disasm` 可选组请了回来——**否决的是"硬依赖"，不是"能力本身"**；一旦能以懒加载+优雅降级容纳，重依赖也能进门。

**可复用的设计原则**：**依赖分级：核心路径零重依赖；增强能力做成可选组 + 运行时探测 + 带安装指引的降级错误**。"否决一个依赖"和"永远不要它"是两回事，留好门。

#### D10. Windows 平台聚焦

**背景/痛点**：跨平台内存后端意味着三套 API、三套权限模型、三倍测试矩阵，而目标游戏绝大多数跑在 Windows。

**采纳方案**：本版本仅实现 Windows 后端（ctypes 直调 kernel32：OpenProcess/ReadProcessMemory/WriteProcessMemory/VirtualQueryEx）；非 Windows 平台 `get_backend()` 显式抛 `E_UNSUPPORTED_OS`，不伪装支持。

**备选与否决理由**：早期决策，无正式记录。缓解设计：后端抽象为 `MemoryBackend`，Linux/macOS 后端是"规划项"而非"伪实现"。窗口标题 attach 等 Windows 特性（EnumWindows）也在此边界内实现。

**可复用的设计原则**：**平台聚焦时，把"不支持"做成显式错误码而不是静默失败**；抽象层留好缝，未来的平台后端是新增文件而不是重构。

### 分析能力层（D11–D17）

#### D11. confidence + evidence 输出约定

**背景/痛点**：布局分析、引擎检测全是启发式。如果只输出结论，AI 会把 0.3 置信度的猜测当事实去写内存。

**采纳方案**：所有启发式结果强制携带 `confidence`（0–1）+ `evidence`/`reason` 字段。引擎检测返回 `{"engine", "confidence", "evidence": [...]}`；布局分析候选带 `{address, confidence, reason}`；UE 内省输出 `{verdict, confidence, hypotheses}`。且低置信结果不阻断，交由 AI 决策。

**备选与否决理由**：P4 计划"参考项目借鉴"明确取自 ida-pro-mcp 的"置信度输出"模式；风险表补充约束："布局分析启发式误报误导 AI 写入 → 强制 confidence 字段；结果不直接接 modify，需 name set 确认"。被否决的替代是"只输出 top-1 结论"——无法传递不确定性。

**可复用的设计原则**：**启发式系统的输出协议必须内建不确定性通道（分数+证据），并在流程上禁止低置信结论直接触发副作用**。

#### D12. UE 内省：可验证假设探测 vs 硬编码偏移

**背景/痛点**：UE 游戏的 GObjects/GNames 偏移随版本/魔改引擎漂移，硬编码偏移表必然过时；而 AI 需要结构事实才能枚举 Actor。

**采纳方案**：`engines/ue_introspect/layout.py` 做**假设探测**：对候选步长 {配置值, 0x18, 0x20} 抽样打分（判据 = Object 指针形状通过率 + SerialNumber 单调性），FNamePool 按 UE4 线性/UE5 两级双假设探测（判据 = 解码字符串可打印比例），输出 confirmed/partial/failed 三级结论；探测失败不抛异常，返回 verdict=failed + 每个候选的 evidence。

**备选与否决理由**（UE 计划 Rejected Alternatives）：
1. 6 文件大子包拆分（hypothesis.py/uobjectarray.py 等）——对本规模过度，合并为 layout/fname/actors 三文件；
2. 修改 `engines/unreal.py` 集成运行时探测——unreal.py 定位是离线 dumper 输出解析（无 backend），混入在线探测破坏职责边界，新子包与其互补。

**可复用的设计原则**：**面对跨版本漂移的内存结构，用"采样+判据打分"的可验证假设代替静态知识表；探测失败也要输出结构化证据，把决策权（而非崩溃）交给上层**。

#### D13. 邻近归组批读 vs read_many（规避 per-address VirtualQueryEx）

**背景/痛点**：UE Actor 枚举要读数万个散列指针。通用 `read_many` 对每个地址做 VirtualQueryEx 区域校验，5 万地址下系统调用是灾难。

**采纳方案**：`ue_introspect/actors.py` 自研 `_read_span_groups`：地址排序 → 按邻近度（gap ≤ 配置阈值）归组 → 每组一次裸 `backend.read(start, span)` → span 失败退化为组内逐地址读。一次读 0x20 同时覆盖 ClassPrivate(+0x10) 与 FName(+0x18)。三级批量管道把系统调用从 ~60 万降到 ~3000–7000（降 99%）。

**备选与否决理由**（UE 计划 Rejected Alternative #5）："用 read_many 做散列指针批读——per-address VirtualQueryEx 在数万地址下慢一个量级；自研邻近归组（不调 query）是正确方案"。P4 计划 4.1 也记录了对偶决策：scanner 的 next_scan 批量读按 region 归组（"将 2 万次系统调用降为数百次"），并保留 `use_batch_read` 逐地址回退路径。测试用 FakeBackend 读计数器断言"枚举 N 对象读次数 ≤ O(chunks+groups) 而非 O(N)"。

**可复用的设计原则**：**批量 API 设计前先分析系统调用开销模型：当逐条校验成本占主导时，"排序+邻近归组+整段读+失败退化"优于逐条封装；并用计数器测试把性能契约固化成断言**。

#### D14. 指针扫描三层缓存

**背景/痛点**：指针扫描（反向 BFS 找指针链）昂贵且结果庞大；候选集内嵌 session JSON 会让会话文件膨胀；进程重启后缓存还会失真。

**采纳方案**：三层结构——(1) 内联层：路径数 ≤ 500 全量返回，超出只回 20 条样本 + 总数；(2) sidecar 层：全量路径持久化到 `sessions/<id>/pointer_paths.bin`，供 `pointer-scan --rescan` 复用验证；(3) 新鲜度层：扫描状态携带 `region_fingerprint`（region base/size 哈希），进程重启/布局变化时强制失效并抛 `E_SCAN_CACHE_STALE`。候选集超阈值同样外置 `scan_candidates.bin`。

**备选与否决理由**（P4 计划 Rejected Alternative #4）："候选地址磁盘缓存替代 session 内嵌——会破坏 scan/scan-next 语义契约；采用 sidecar 外置 + fingerprint 校验的折中方案"。风险表补充："缓存陈旧（进程重启/ASLR）→ region fingerprint 校验 + attach 时强制失效 + 显式错误码"。

**可复用的设计原则**：**昂贵计算的结果缓存要回答三个问题：多大的结果该离开主通道（阈值外置）？缓存怎么跨调用复用（sidecar）？什么时候必须作废（指纹+显式失效错误码）？**

#### D15. 异步任务框架 vs 同步超时

**背景/痛点**：同步 pointer-scan 有 30s 预算（`E_SCAN_TIMEOUT`），深一点的扫描必超时，且超时即丢结果——工作白做。

**采纳方案**：`jobs.py` 后台作业框架：`pointer_scan async_run=true` 立即返回 `job_id`，`job_status` 轮询 depth/paths_found 进度，结果在状态翻转前持久化到 `sessions/<id>/jobs/<job_id>.json`；`job_cancel` 协作式取消且**部分结果保留**。同步路径与三重资源上限（max_depth/max_paths/timeout）保留不动。

**备选与否决理由**：P4 计划 Rejected Alternative #2："multiprocessing 常驻并行扫描——HANDLE 跨进程传递复杂度高；线程池 + numpy 已足够，multiprocessing 仅作备选"——同一逻辑：不为长任务引入重量级机制。P4 风险表："指针反向扫描组合爆炸 → max_depth/max_paths/timeout 三重上限 + truncated 标记"，异步框架是其上的第二层兜底。

**可复用的设计原则**：**长任务的正确形态是"立即返回句柄 + 可轮询进度 + 结果先落盘再改状态"；取消和超时都不允许丢掉已完成的工作**。

#### D16. capstone 选型（从被否决到可选依赖请回）

**背景/痛点**：解读 `find-writers` 返回的 RIP、反汇编游戏函数需要运行时反汇编能力。

**采纳方案**：`analysis/disasm.py` 基于 capstone，注册为 `disasm` 可选依赖组；未安装时返回 `E_DEPENDENCY_MISSING` + hint（`pip install game-modifier[disasm]`），不阻塞其他功能。

**备选与否决理由**：这是一次"迟到的采纳"。P4 计划 Rejected Alternative #3 曾否决"引入 capstone/keystone 等重依赖——违反最小依赖原则"，当时 vtable/RTTI 全部用结构化启发式实现。P6 阶段反汇编成为明确需求时，capstone 以**可选组+懒加载**身份进入——D9 的降级框架让"重依赖"不再与"最小核心"冲突。keystone（汇编器）始终未引入，因为只需要读不需要写指令。

**可复用的设计原则**：**选型被否往往是否决"进入方式"而非"能力本身"；当架构有了降级容器（可选依赖+懒加载+错误码），旧否决可以被体面地翻案**。

#### D17. radare2 r2pipe 桥接 vs 重型分析框架

**背景/痛点**：交叉引用分析（谁写了这个地址）需要静态分析引擎，但内嵌完整反编译框架违背工具定位。

**采纳方案**：`toolchain/radare2.py` + r2pipe 可选组桥接外部 radare2/rizin 进程；`xrefs` 为只读工具；radare2 未安装时返回 `E_TOOL_NOT_FOUND` + 安装 hint（`winget install radare2`），功能优雅缺席。

**备选与否决理由**：计划文件未记录与 Ghidra/IDA 的直接对比表，但两条实际记录指向同一取舍：P4 Rejected Alternative #3（最小依赖原则，不引重型框架）与 #5（"不照搬 ida-pro-mcp 自研架构，仅吸收设计思想"）。选择 r2pipe 而非 headless Ghidra 的现实理由也写在工具链文档：radare2 可用 winget 一行安装，启动即脚本化，符合"外部工具自动探测、缺失给 hint"的既有模式。

**可复用的设计原则**：**桥接外部重型工具优于内嵌：用"探测→缺失给安装指引→存在则薄封装"的适配器模式，把大框架的演进风险留在项目外**。

### token 效率层（D18–D22）

#### D18. 临时符号 + name chain 链中间态

**背景/痛点**：指针链每一级的中间地址，Agent 都要手算再传回——token 浪费且易错。

**采纳方案**：`name chain` 一次调用注册整条链：`mgr.step0..stepN` 中间态符号自动生成；默认 temp（`name clear-temp` 一键清理），持久符号另走 `name set`。地址算术（`0x...+/-0x...`）也在服务端求值（`value_convert` 同族），Agent 永不手算地址。

**备选与否决理由**：早期决策，无正式记录。对照动机（AGENTS.md "Why this saves tokens"）："符号地址表：引用 player.gold，永不用原始指针链"、"内置地址算术——永不手算地址"。被隐含否决的替代是"Agent 侧逐级 resolve"——把计算推回 LLM 正是 token 效率的反面。

**可复用的设计原则**：**凡是确定性可计算的中间步骤，都应在服务端折叠成一次调用并留下可引用的中间产物；LLM 只负责意图，不负责算术**。

#### D19. 宏系统参数化复用

**背景/痛点**：同一套"扫描→命名→修改→冻结"操作序列在不同数值上反复出现，每次重新描述浪费 token。

**采纳方案**：`macro_define/show/list/run/delete`：宏定义持久化为 `sessions/<id>/macros/<name>.yaml`，参数化复用；与 profile 联动（symbols 档允许定义但不允许 run）。

**备选与否决理由**：无正式记录。对照同层替代：template（静态 YAML 预设，面向通用游戏类型）与 batch（面向一次性批量操作）。宏补的是"会话内可复用的动态操作序列"这一层，三者不重叠——这也是它没被 template 吞并的原因。

**可复用的设计原则**：**为 AI 客户端提供"把已验证的操作序列固化成可参数化资产"的能力，复用粒度（模板/批处理/宏）按生命周期区分**。

#### D20. MCP 工具分组按需加载

**背景/痛点**：83 个工具的 schema 全量注册，每次会话的上下文成本可观；很多场景只需要 core+scan。

**采纳方案**：`TOOL_GROUPS` 9 分组（core/scan/modify/analysis/ue/il2cpp/jobs/macros/safety），`--groups core,scan` 只注册所选组；`tools_catalog` 永远注册用于自发现；profile 机制独立叠加在分组之上。

**备选与否决理由**：无正式记录。设计动机见 AGENTS.md："start the server with --groups core,scan to register only those groups and cut per-call context cost"。被隐含否决的替代是"单一工具集+文档裁剪"——schema 注册成本是真实的，物理不注册才是真省。

**可复用的设计原则**：**MCP 服务的工具面要模块化：按使用场景分组、按需注册、保留一个永远在场的目录工具供客户端自发现**。

#### D21. 会话快照

**背景/痛点**：探索性修改（试几组地址、临时符号满天飞）容易把 session 搞乱，想回到"干净状态"只能重 attach。

**采纳方案**：`session snapshot <name>` 把会话状态存为 `sessions/<id>/snapshots/<name>.json`；restore 前自动把当前状态归档为 `<name>.pre-restore.json`——恢复操作本身也可回滚。

**备选与否决理由**：无正式记录。UE 计划风险表有一条相关取舍："Session JSON 膨胀 → v1 仅缓存布局假设（小），枚举结果不落盘；sidecar 快照留作 v2"——快照刻意保持轻量，只存状态元数据不存大体量结果。

**可复用的设计原则**：**有状态系统要给客户端"存档/读档"原语，且读档前自动备份当前态——让每次恢复都可撤销**。

#### D22. batch 结果落盘分页 vs 截断

**背景/痛点**：batch_run 可能产生超大结果。早期通用限流会做二分截断——恰好把批量结果拦腰砍断，数据丢失。

**采纳方案**：**完整结果永远落盘** `sessions/<id>/batch_results/<ts>.json`（`results_file` 返回给调用方）；内联窗口用 `offset/limit` 分页；超限时内联只给 summary + 前 10 条 + results_file 指引。AGENTS.md 明确："对大结果集永远从 results_file 取数，不要依赖截断预览"。

**备选与否决理由**：P4 计划 5.1 的通用限流（preview + total + 落盘路径，借鉴 mrexodia/ida-pro-mcp rpc.py）是基础方案；batch 被专门豁免于"二分截断"，因为批量结果的每一条都可能是 Agent 下一步分支的依据，丢一条就错一片。5.6 同时要求逐项错误格式 `[{op, ok, error}]`——"单项失败不中断整批"。

**可复用的设计原则**：**"截断"和"分页"是两种语义：截断丢数据，分页不丢。凡是调用方需要全量事实的输出，永远全量落盘 + 窗口化内联，禁止破坏性截断**。

### 安全增强层（D23–D27）

#### D23. 多级 profile 5 档

**背景/痛点**：不同部署场景的信任度不同：生产托管要只读，试验环境允许小改，完全信任才给批量写。二值开关（default/readonly）颗粒度不够。

**采纳方案**：5 档 `PROFILES`：default（全部）/ readonly（只读，注册时排除写工具）/ dry-run（写工具在场但 confirm=true 被服务端以 `E_PROFILE_RESTRICTED` 拒绝）/ symbols（只读+符号管理+快照+宏定义）/ limited（只读+modify/nl，排除 batch/freeze/template 批量写）。历史两档行为逐字冻结，新档位纯增量。

**备选与否决理由**：P4 计划 5.5 引入只读 profile 时明确限定："支持 --profile readonly 启动参数：仅暴露只读工具（供保守 AI 场景）"，且"现有全部 MCP 工具签名与返回结构零改动"。后续扩档遵循同一铁律——被否决的替代是"修改 readonly 语义以容纳新能力"，代码注释原文："default and readonly keep their historical behavior exactly; the extra tiers are additive"。

**可复用的设计原则**：**权限分级要"历史档位行为冻结 + 新档位纯增量"：升级安全模型的正确方式是加新档，不是改旧档**。

#### D24. 运行时安全档位切换

**背景/痛点**：profile 是启动参数，会话中途想临时收紧（例如让 Agent 只做预览）必须重启服务器。

**采纳方案**：`safety_get_level` / `safety_set_level`（CLI `safety level [--set ...]`）：进程级 `normal` ↔ `dry_run_only` 热切换；`dry_run_only` 下所有确认写入被 `_gate_write` 前置拦截（`E_PROFILE_RESTRICTED` + hint 告知如何恢复）。进程作用域、不持久化——重启回到默认。

**备选与否决理由**：无正式记录。设计取舍清晰：持久化档位会引入"忘了开回来"的隐患，进程作用域把影响面限制在单次服务器生命周期；且 `safety_set_level` 本身被 readonly profile 排除——收紧可以自助，放宽必须重启。

**可复用的设计原则**：**安全档位要支持运行时收紧但放宽受控；临时性安全状态用进程作用域而非持久化，避免安全设置被时间腐蚀**。

#### D25. dry-run 明确状态字段

**背景/痛点**：dry-run 预览与真实失败、真实成功如果形状相似，Agent 会误判"已经改了"。

**采纳方案**：dry-run 走独立信息性错误码 `E_DRY_RUN`（注释明言 "informational, not a hard failure"），预览输出带 `impact` 字段（region 信息、旧值/新值、将创建的备份）。写入口返回 `status=preview`，Agent 可明确区分三态。

**备选与否决理由**：P4 计划 1.4 的约束原文："dry-run 分支追加 impact 字段——仅新增字段不删改"；风险表："dry-run 输出字段变化破坏现有断言 → 仅新增 impact 字段，不删改现有键"。被否决的替代是"复用普通成功响应加个 flag"——会污染成功语义，让 ok=true 不再等于"已生效"。

**可复用的设计原则**：**预览/模拟态必须有独立的协议表达（专属状态码+影响面描述），且演进时只加字段不动旧键——机器客户端对"将要发生"与"已经发生"的区分必须是零歧义的**。

#### D26. batch 风险分级（代码段写入需 --confirm-code）

**背景/痛点**：批量写入里混进指向可执行段/只读段的目标，一次 confirm 就全部放行——风险不对等。

**采纳方案**：batch 按目标 region 分级：`risk=normal`（可写数据段）在普通 confirm 下执行；高风险目标（可执行/只读/未知 region）默认跳过并记 `skipped_reason="high_risk_requires_confirm_code"`，只有额外的 `confirm_code=true`（CLI `--confirm-code`）才放行；summary 汇总 `skipped_high_risk` 计数。

**备选与否决理由**：无正式记录。对照被隐含否决的替代："高风险直接报错中断整批"——与 D22 的逐项错误哲学冲突（单项问题不该杀死整批）；"高风险静默跳过不报告"——违反透明原则。跳过+显式原因+二级开关是三者折中。

**可复用的设计原则**：**批量写操作要按目标风险分级门控：常规确认覆盖常规风险，升级风险需要升级确认，且被拦下的项必须可审计、不连坐**。

#### D27. DEFAULT_HINT 机制（显式优先）

**背景/痛点**：错误码解决了"分支"，但 Agent 常不知道"下一步做什么"。每个 raise 点手写 hint 又会漏。

**采纳方案**：`GameModifierError` 基类提供类级 `DEFAULT_HINT` 兜底；高频可行动错误码（E_ANTI_CHEAT/E_NEEDS_SCAN/E_SYMBOL_NOT_FOUND/E_TOOL_NOT_FOUND/E_DEPENDENCY_MISSING 等）在异常子类覆写默认 hint；**显式 `hint=` 参数永远优先于类默认**（源码注释原文："An explicit hint= argument always wins over the class default"）。

**备选与否决理由**：源自 retrospective 的改进项："errors.py 每个错误加 plain_hint（人话）+ expert_hint"。落地时选择了更克制的单 hint 字段 + 类级默认机制，被隐含否决的替代是"集中式错误码→hint 映射表"——hint 与异常类就近定义，改错误码时不会忘了改另一个文件。

**可复用的设计原则**：**给机器的错误要自带下一步指令；hint 的供给机制要"就近默认 + 现场覆盖"，保证任何错误路径都有出路，同时允许调用点精确化**。

### 引擎集成层（D28–D32）

#### D28. field_chain vs pointer_chain 语义分离

**背景/痛点**：实战事故（retrospective §3）：`modify(address=0x21EF..., offsets=0x4)` 本意是结构体字段偏移（base+4），但代码按 Cheat Engine 指针链语义先解引用，读出垃圾大数再 +4，得到无效地址 `E_INVALID_ADDRESS`。**同一组参数承载两种语义，必然出事故。**

**采纳方案**：`memory/pointers.py` 的 `resolve_pointer` 支持三种模式：`relative`（直接相加）/ `pointer_chain`（先解引用再偏移，CE 语义）/ `field_chain`（先偏移再解引用，嵌套结构体字段）；`_default_mode` 智能默认：纯绝对地址+offsets 默认 relative，`module.dll+0x..` 默认 pointer_chain；均可显式 mode 覆盖；read/modify/name_set/name chain/resolve 全链路透传，resolve 输出每级 trace 供语义自查。

**备选与否决理由**：retrospective 记录的第一版修复是"智能默认"（绝对地址降级 relative）；field_chain 是后续补充的第三态——因为嵌套结构体需要"偏移→解引用"的相反顺序，二态模型表达不了。被否决的替代是"让 Agent 自己分步读指针"——回到手算地址的老路。修复验证走"失败测试先红→修复后绿"的反馈环。

**可复用的设计原则**：**一个参数出现语义歧义事故后，正确解法是"显式枚举所有语义 + 可预测的智能默认 + 全链路 trace"，而不是打补丁式猜测；修复必须用红绿测试锁定**。

#### D29. il2cpp 转储指纹失效检测

**背景/痛点**：`il2cpp dump` 产出的 script.json/dump.cs 与特定游戏二进制绑定；游戏更新后旧转储的 RVA 全部错位，继续用会指错地方且毫无报错。

**采纳方案**：dump 时记录游戏二进制的 `(size, mtime)` 指纹（`engines/unity_lookup.py` 的 `_fingerprint`）存入 session；后续 `il2cpp lookup` 前校验指纹，二进制变化则拒绝并要求重新 dump；`--force` 显式跳过校验。script.json 解析也按指纹缓存（"matching fingerprint = sub-second"，389MB 文件免全量重解析）。analyze 输出 `dump_stale` 字段主动暴露陈旧状态。

**备选与否决理由**：无正式记录。对照 D14 的同构逻辑：缓存必须配失效判据。被隐含否决的替代是"信任转储永久有效"（retrospective 的教训正是工具矩阵过时/产物错位）与"每次全量重 dump"（17 秒~20 分钟成本不可接受）。

**可复用的设计原则**：**任何"产物 ↔ 源"的派生缓存都要记录源指纹并在消费前校验；陈旧不是异常而是状态，主动暴露并提供 --force 逃生门**。

#### D30. Unity 加密存档密钥不落盘

**背景/痛点**：部分 Unity 游戏存档是 `Base64(DES-CBC(JSON))`，密钥硬编码在游戏代码里，编辑存档必须提供 key/IV。密钥属于敏感信息，不能进 session 文件（会被快照、备份、日志带走）。

**采纳方案**：`save_edit/unity.py` 明确要求 key/IV "used in memory and never persisted to session state"；CLI 走 `--key`/`--iv`，MCP 走参数传递；缺密钥时报错并附 hint："密钥不落盘"。需要密钥的处理器被标记 `requires_key=True` 做路径级门控。

**备选与否决理由**：无正式记录。被隐含否决的替代："密钥存 session 方便复用"（泄露面失控）、"密钥存配置文件"（脱离会话生命周期，多游戏混淆）。pycryptodome 也为此做成独立 `crypto` 可选组——加密能力只在真实需要时入场。

**可复用的设计原则**：**敏感凭据走"参数进、内存用、不落盘"通道；持久化边界就是泄露边界，任何会进文件的状态都要先问一句"它配被持久化吗"**。

#### D31. 工具链 AI 推荐安装流程

**背景/痛点**：retrospective 实录：Il2CppDumper 不支持 metadata v39 → Cpp2IL 失败 → Il2CppInspector 失败 → 靠人工 GitHub 搜索才发现 il2cpp-dumper-rs，光 cargo 编译就 20 分钟。**探测到缺失≠引导安装，用户在 E_TOOL_NOT_FOUND 上碰壁三次。**

**采纳方案**：`toolchain/registry.py` 增加 `metadata_version()`（读 global-metadata.dat magic+版本）与 `recommended_unity_dumper()`（≤31 官方 Il2CppDumper，>31 il2cpp-dumper-rs）的引擎版本→工具路由表；错误码带可执行 hint；AGENTS.md 固化标准流程："告知缺什么+为什么重要 → 给确切安装命令 → 用户确认后执行 → toolchain detect 验证 found:true → 重试原命令"，只有用户拒绝才降级。

**备选与否决理由**：retrospective 否决的替代是"被动等用户搜索"（"关键教训：工具链推荐必须在 attach 成功那一刻主动给出"）；同时 `[tools.auto_install]` 自动安装被设为默认 false——推荐要主动，执行必须经用户确认，这是与 D5 一致的门控哲学。

**可复用的设计原则**：**依赖缺失的用户体验三段式：版本感知的路由表（选对工具）→ 错误即安装指引（给确切命令）→ 验证闭环（装完确认可用再重试）；自动化安装永远保留人工确认闸门**。

#### D32. save_edit 存档型游戏分流

**背景/痛点**：RPG Maker / Ren'Py 游戏的数据活在存档文件里，内存扫描注定徒劳；更糟的是 NW.js 家族游戏带 `.pak` 文件，曾被误判为 Unreal 引擎，把 Agent 引向完全错误的分析路径。

**采纳方案**：(1) 检测层：新建 `engines/nwjs.py` 多特征加权检测（NW.js/RPG Maker/Ren'Py），`_scan_unreal` 加排除标记（nw.dll/index.html/rmmz_core.js 存在即跳过 Unreal），裸 .pak 置信度 0.55→0.35；(2) 分流层：检测结果带 `save_edit: True` 标记 → session 注入 `save_edit_info` → 内存扫描类错误返回 `E_SAVE_EDIT_REQUIRED` 引导走 `save-edit detect/modify`；(3) 不可编辑格式（Ren'Py pickle）明确 `E_SAVE_FORMAT_UNSUPPORTED` 且"do not retry"。

**备选与否决理由**（引擎检测计划 Rejected Alternatives 原文）：
1. 加权评分矩阵（每个特征数字权重累加）——"过度工程化，引入复杂的评分调参问题；简单的'否定优先级'（检测到 NW.js 特征→跳过 Unreal）更直观、可维护、不易出错"；
2. 修改现有 `_scan_unreal()` 内部逻辑处理排除——"违反单一职责原则；Unreal 检测应只关注 Unreal 特征，排除逻辑应在调度层处理"；
3. 自动选择 NW.js 主进程（多进程时选内存最大者）——"可能选错（NW.js 的 GPU 进程有时内存最大）；返回候选列表让用户确认更安全"。

**可复用的设计原则**：**多特征识别优先用"否定优先级"（强特征命中即排除竞争者）而非全局评分调参；检测出的"此路不通"要变成显式分流信号（错误码+替代路径），而不是让调用方在死路上反复尝试；拿不准的多候选场景永远返回列表让人选，不自动猜**。

## 5. 总结：10 条可迁移的设计原则

1. **信封即契约**（D2/D4）：面向机器的接口，输出结构与错误码值就是 ABI——只追加，不改值，不混入人类可读噪音。
2. **追加式演进 + 测试基线门**（D4/D8/D23）：枚举、字段、profile、方法全部追加式扩展；"基线测试数不下降"作为硬性回归门，让重构永远有安全网。
3. **安全默认拒绝，显式确认，服务端兜底**（D5/D6/D23/D24/D26）：默认态无害（dry-run/只读），副作用需显式 confirm，风险分级配二级确认，且服务端永远保留否决权——防线可叠加，不可放宽。
4. **会话化一切昂贵上下文**（D3/D18/D20/D21）：attach 一次、符号寻址、地址算术服务端代劳、工具按需注册——token 效率不是优化项，是架构目标。
5. **批量 API 先算系统调用账**（D13/D22）：设计批接口前先建模 per-item 开销；全量结果落盘 + 内联分页，禁止破坏性截断。
6. **启发式必须输出不确定性**（D11/D12）：confidence + evidence 进协议，探测失败返回证据而非异常，低置信结论禁止直接触发写入。
7. **缓存三件套：阈值外置、sidecar 持久化、指纹校验失效**（D14/D29）：任何派生缓存都要能回答"多大外置、如何复用、何时作废"。
8. **可选依赖 + 懒加载 = 否决的翻案机制**（D9/D16/D17）：核心零重依赖，增强能力装进可选组与降级错误码；桥接外部重型工具优于内嵌。
9. **错误必须自带下一步**（D27/D31/D32）：hint 就近默认 + 现场覆盖；依赖缺失给安装命令；此路不通给分流路径。
10. **长任务不丢工作**（D15/D7）：异步句柄 + 进度轮询 + 结果先落盘；每次副作用留审计与回滚凭证。
