# 决策复盘 · AI 协作案例版

> 项目：game-modifier（单机游戏内存修改工具 CLI/MCP 插件）
> 日期：2026-08-14
> 读者：对 AI 多智能体协作开发感兴趣的工程师
> 姊妹篇：01/02 为决策清单与架构复盘，04 为对外分享版；本篇聚焦**多智能体如何分工、并行、解决冲突**的开发过程方法论。

---

## 1. 引言

game-modifier 是一个为编码 Agent（Claude Code / Codex CLI 一类工具）设计的
Token 高效单机游戏内存修改插件：`attach` 一次拿到 session，之后用符号表、
中文 NLP、模板与批处理把"改金币"这类操作压缩成最少的工具调用。

它的特殊之处在于：**这个项目本身就是由 AI 多智能体协作开发的**——从需求分析、
方案规划、编码实现、测试验证到文档收尾，全程由一个 Leader 智能体编排多个
专职子智能体完成。开发过程历经 8 轮重大迭代，测试基线从 83 个用例增长到
687 个（截至 2026-08-14 实测；当前基线 **858**，以 `scripts/refresh_metrics.py` 输出为准），MCP 工具从 24 个扩展到 83 个，且**每一轮
迭代零回归**。

这篇复盘回答一个问题：当多个 AI 智能体同时改同一个代码库时，靠什么机制让
它们不打架、不重复劳动、不破坏彼此的成果？以下机制全部来自真实执行记录，
不是理论推演。

## 2. 协作架构：Leader-Agent 编排模型

### 2.1 Leader 的职责边界

Leader 智能体**不直接写代码**。它的职责是五个动词：

| 职责 | 具体动作 |
| --- | --- |
| **规划** | 把用户痛点转化为分阶段实现计划（含依赖图、测试计划、Rejected Alternatives） |
| **分解** | 把计划切成可独立验收的任务，标注 blockedBy 依赖 |
| **调度** | 决定哪些任务串行、哪些并行，派发给哪类智能体 |
| **验证** | 每个任务回收后核对验收标准，阶段收尾跑基线验证门 |
| **综合** | 汇总多视角方案择优，处理智能体间的冲突报告 |

这条边界很重要：Leader 一旦亲自下场写代码，就会失去全局视野，无法同时跟踪
并行任务的状态。实测中 Leader 只出现过一次"直接改文件"，是修文档里的一个
数字漂移——即便如此也走的是同样的验证流程。

### 2.2 五类智能体分工

| 类别 | 角色定位 | 典型产出 |
| --- | --- | --- |
| **Research 智能体** | 调研与规划，不碰代码 | 实现计划（含阶段划分、依赖图、风险表、Rejected Alternatives） |
| **Coding 智能体** | 按计划的锚点实现，不扩大范围 | 代码 + 测试 + 验证输出 |
| **Verify 智能体** | 全量回归、wheel 重建、CLI 冒烟 | 基线数字（测试数 / 工具数 / 覆盖率） |
| **文档智能体** | 收尾阶段同步全部文档数字 | AGENTS.md / USER_MANUAL.md 等一致性更新 |
| **评审智能体** | 复盘阶段，对照决策清单审查 | 决策复盘文档（本系列） |

Research 与 Coding 的分离是刻意的：让规划者不带实现包袱地出方案，让实现者
不夹带私货地执行计划。UE 内省功能的实现智能体连"禁止用 read_many 做散列
批读"这种反直觉约束都照单执行——因为计划里写明了理由（per-address
VirtualQueryEx 在数万地址下慢一个量级）。

### 2.3 任务依赖图管理（blockedBy 机制）

每个任务声明自己的前置依赖。调度器只派发 blockedBy 已全部完成的任务，
这天然形成了"串行关键路径 + 并行独立分支"的拓扑。三份计划文件里的依赖
段落直接映射成任务边：

```
引擎检测修复与扩展：
  阶段1(引擎检测) → 阶段2(存档分流)   ← 依赖新引擎常量
  阶段1(引擎检测) → 阶段3(窗口attach) ← 依赖 NW.js 多进程结论
  阶段2 ∥ 阶段3                       ← 文件集不相交，可并行

高级分析与性能优化：
  阶段一(安全+read_many) → 阶段四(性能)  ← 批读依赖 read_many
  阶段二(AOB) ∥ 阶段三(布局分析)        ← 不同文件集
  阶段五(MCP升级) 依赖 二三四 service 方法就绪
```

关键经验：**计划文件必须显式写出"哪些阶段可并行、为什么"**（文件集不相交 /
依赖哪个接口就绪），否则调度只能保守全串行，浪费并行窗口；或者盲目全并行，
撞文件冲突。

## 3. 关键协作机制

### 3.1 三视角并行规划

**机制**：重大功能开工前，Leader 同时派 3 个 Research 智能体，各自从
**简洁性 / 性能 / 最小变更**三视角独立出方案，互不可见对方产出；Leader
收齐后综合评审，择优融合成最终计划。

**实例：UE 结构内省功能（ue introspect / actors / fname）**

| 视角 | 方案要点 | 最终去向 |
| --- | --- | --- |
| 简洁性（方案 A） | 6 文件大子包：hypothesis.py / uobjectarray.py 等独立文件 | **否决**：对本规模过度设计；收敛为 layout / fname / actors 三文件子包 |
| 性能（方案 B） | 增量枚举 `--since-serial` + sidecar 快照持久化 | **延后到 v2**：缓存失效与快照管理复杂度超 v1 需要；limit/filter + 类链缓存已够用 |
| 最小变更 | 不新增错误码、不新增依赖、全部追加式 | **采纳为硬约束**：复用现有 `E_LAYOUT_UNSUPPORTED`，否决了新增 `E_UE_LAYOUT_INVALID`（语义重叠） |

三视角的产出不是三选一，而是**融合**：最终计划采纳了方案 B 的性能设计核心
（三级批量读管道 + 三层缓存，把 50,000 对象枚举的系统调用从约 60 万次降到
3,000–7,000 次），同时用最小变更视角约束住了范围（明确拒绝"修改
engines/unreal.py 集成运行时探测"——unreal.py 定位是离线 dumper 输出解析，
混入在线探测破坏职责边界）。

**为什么值得**：单视角规划要么过度工程（只追性能），要么范围失控（只追
功能完备）。三视角强制把"取舍"显式写进计划的 Rejected Alternatives 段落，
后来者能看到每个被拒方案的理由，复盘时也能核对当初的假设是否成立。

### 3.2 锚点隔离并行

**机制**：多个 Coding 智能体需要同时修改 `service.py` / `cli.py` /
`mcp_server.py` 这类"共享枢纽文件"时，任务提示中用"**文件 + 区块锚点**"
划定各自的写入区域，锚点之外的代码一律只读。

**实例一：临时符号（name chain）与宏系统并行**

两个功能都要在 service.py 新增方法、在 cli.py 新增子命令、在 mcp_server.py
注册工具。派发指令明确：

- 智能体 A（name chain）：service.py 锚定在符号表区块（name_set 附近）追加
  `name_chain` / `name_clear_temp`；cli.py 锚定 `name` 子命令组；MCP 锚定
  符号工具注册块。
- 智能体 B（宏系统）：service.py 锚定文件底部新增宏区块；cli.py 新增独立的
  `macro` 子命令组；MCP 在独立注册块追加。

两者的测试文件也天然隔离（test_name_chain.py vs test_macros.py），互不引用。

**实例二：多级 profile 与风险分级并行**

- 智能体 A：mcp_server.py 的工具注册过滤逻辑（readonly / dry-run / symbols /
  limited / default 五档 profile）。
- 智能体 B：运行时安全档位（safety_get_level / safety_set_level，
  `dry_run_only` 拒绝一切确认写入）——锚定 service 层与安全层，不碰工具
  注册过滤。

**锚点话术模板**（摘自实际任务提示）：

> ⚠️ 另一智能体正在并行修改同一文件的 `<其他区块>`。你只允许在 `<锚点区块>`
> 追加代码，不得移动、重排或删除锚点之外的任何行。新增测试写入独立文件
> `tests/test_<功能>.py`，不得修改其他智能体的测试文件。

### 3.3 追加式实现 + 向后兼容铁律

**机制**：每轮迭代的验收标准之一是"**测试基线只增不减**"。计划文件把这条
写成硬约束，例如：

- 引擎检测修复计划：「回归保护：所有 290 个现有测试必须继续通过」
- 高级分析计划：「基线测试数不下降且全部通过（以 pytest --collect-only 实测为准）」
- UE 内省计划：「408 个现有测试零回归，不新增错误码，不新增依赖」

支撑这条铁律的配套约定：

| 约定 | 目的 |
| --- | --- |
| 错误码只追加不修改（40 个码值一经发布即冻结） | Agent 消费者依赖码值分支 |
| `MemoryBackend` 新方法禁止 `@abstractmethod`，一律具体默认实现 | 保护 FakeBackend 测试替身（高级分析计划原文：「会破坏 FakeBackend 和全部测试」） |
| Session 新字段用 `default_factory=dict` + `from_dict` 用 `.get()` 容错 | 旧 session JSON 无需迁移 |
| 新功能先落 service.py，再同步暴露到 CLI 与 MCP 两壳 | 防止双表现层行为漂移 |

**测试基线演进**（截至 2026-08-14 实测）：

| 迭代 | 基线 | 增量来源 |
| --- | --- | --- |
| 初始核心 | 83 | CLI/NLP/安全/会话基础 |
| 引擎检测与分流 | 290 | MCP 扩展、引擎检测、存档分流、窗口 attach |
| 高级分析与性能 | 408 | AOB、布局分析、指针反查、MCP 升级 |
| UE 内省 + 逆向增强 | 495 | 内省三命令、disasm/watch/xrefs、find-writers/dissect |
| 后续迭代 | 579 → 686 → 687（当前 858） | 错误 hint、宏/快照/异步任务、field_chain |

### 3.4 基线验证门

**机制**：每个阶段收尾、以及并行任务合并后，Verify 智能体执行固定的三道门：

1. **全量回归**：`pytest tests/` 全绿，且用例数 ≥ 阶段入口基线；
2. **wheel 重建**：`python -m build --wheel` 后用 `python -m zipfile -l`
   核对新模块确实被打进包（这个动作是被真实事故逼出来的，见 §5.1）；
3. **CLI 冒烟**：`<新命令> --help`、`--profile readonly` 启动等。

计划文件把验证门写成阶段六的标准动作（"全量 pytest 确认基线测试数不下降
且全部通过 → wheel 重建验证新模块打包 → CLI 冒烟"），而不是靠智能体自觉。

### 3.5 并行冲突的真实案例与处理

再完善的锚点也有意外。记录在案的两类冲突及处理方式：

**案例一：in-flight 改动导致的"临时测试失败"归属判定**

智能体 A 在 service.py 某方法签名上追加参数的改动尚未完成时，智能体 B 运行
自己的测试套件，报告了一条 TypeError 失败。B 的第一反应是"我的代码有 bug"。
Leader 的判定流程：

1. 看失败栈：异常点落在 A 的锚点区块，不在 B 的改动范围；
2. 查任务状态：A 处于 in-progress，其改动处于半完成状态；
3. 结论：**归属 A 的进行中改动**，B 无需修复，只需在自己的最终验证前等待
   A 完成并重新跑基线。

沉淀出的规则：**测试失败先做归属判定（失败栈位置 × 任务状态 × 锚点范围），
再决定谁修**。盲目让报告者修复会造成双重修改冲突。

**案例二：测试夹具的隐式共享**

两个并行智能体都依赖 `tests/conftest.py` 的 `tmp_config` fixture。UE 内省
计划特意写明「不改 config.py——全部用 config.get("ue", key, default=...)
访问，确保现有 tmp_config fixture 不受影响」——这是规划阶段就预防共享夹具
冲突的例子：新功能走带默认值的动态配置读取，不碰共享 fixture 依赖的属性面。

### 3.6 用户实战痛点驱动迭代

8 轮重大迭代没有一轮是"计划内排期"，全部由真实使用痛点触发。痛点→功能
映射：

| # | 实战痛点 | 触发的迭代 | 代表功能 |
| --- | --- | --- | --- |
| 1 | Agent 需要结构化调用通道而非裸 CLI | 核心插件 + MCP 双模式 | CLI/MCP 双壳、JSON 信封、session 复用 |
| 2 | NW.js 游戏被 .pak 误判为 Unreal；存档游戏内存扫描无效；多进程同名无法 attach | 引擎检测修复与扩展 | 否定优先级检测、save_edit 分流、attach --title |
| 3 | 4.6GB 内存纯 Python 首扫超时；冻结轮询吃 CPU；大候选集撑爆 session JSON | 高级分析与性能优化 | numpy 向量化、邻近归组批读、自适应冻结、sidecar 缓存 |
| 4 | 布局启发式结果误导 Agent 写入；指针链手工推导费时 | 同上 | confidence+evidence 强制输出、pointer-scan 反查 |
| 5 | UE 游戏结构靠预置知识不可靠，逐条读 60 万次系统调用不可行 | UE 结构内省 | introspect 探测、三级批量读 + 三层缓存、FName 解码 |
| 6 | il2cpp 转储产物过期导致地址错乱；工具缺失时只会报错不会引导 | 逆向工具链增强 | 转储指纹校验、工具链推荐安装（AI 驱动安装话术）、disasm/watch/xrefs |
| 7 | 错误信息没有"下一步动作"；批量实验前无法回退会话状态 | 错误 hint + 会话管理 | DEFAULT_HINT 机制（579 测试零回归）、session snapshot/restore、宏系统、异步任务 |
| 8 | ObscuredInt 场景下 offsets 被指针链语义误解（写飞地址）；结构体字段链要手工 3 次 read | 语义分离 | pointer_chain / relative 智能默认 → field_chain 模式（deref_last 控制） |

这个模式的价值：**痛点来自真实使用，所以每个功能都有明确的验收场景**；
复盘时每轮迭代都能回答"当初为什么做"，这正是决策清单（§5.4）能成立的前提。

## 4. 迭代时间线

| 阶段 | 触发痛点 | 投入智能体（典型配置） | 产出 |
| --- | --- | --- | --- |
| ① 核心 CLI 插件 | Agent 需要 token 高效的修改通道 | Research×1 + Coding×1 + Verify | CLI、JSON 信封、符号表、NLP、dry-run/备份（83 测试） |
| ② MCP 双模式 | 结构化工具调用、输出限流、只读部署 | Coding×2（锚点隔离）+ Verify | MCP server、输出限流、value_convert（→290 测试，MCP 工具 24+） |
| ③ 引擎检测修复与扩展 | .pak 误判 / 存档游戏 / 多进程 | Research×1 + Coding×2（阶段2∥阶段3）+ Verify | NW.js/RPG Maker/Ren'Py 检测、save-edit、--title |
| ④ 高级分析与性能优化 | 扫描超时、布局分析缺失 | Research×2（借鉴 ida-pro-mcp 调研）+ Coding×3（阶段二∥三∥四）+ Verify | AOB、analysis 子包、指针反查、五档 profile（→408 测试） |
| ⑤ UE 结构内省 | UE 结构靠猜不可行 | **Research×3（三视角）→ Leader 综合** + Coding×1（单线串行）+ Verify | ue introspect/actors/fname（以 408 为基线零回归） |
| ⑥ 逆向工具链增强 | 转储过期、工具缺失无引导 | Coding×2（锚点隔离）+ Verify | disasm/watch/xrefs/find-writers/dissect、转储指纹、安装推荐（基线 → 495） |
| ⑦ 错误 hint + 会话治理 | 错误无下一步指引、状态不可回退 | Coding×2（hint ∥ 快照/宏/异步任务）+ 文档×1 | DEFAULT_HINT、snapshot/restore、macros、async jobs（579 → 686） |
| ⑧ field_chain 语义分离 | 结构体字段链与指针链语义混淆 | Coding×1 + Verify + 文档×1 | field_chain + deref_last（687 测试，零回归） |

两个节奏规律：

1. **越是高不确定性功能，规划智能体越多、实现智能体越少**。UE 内省用 3 个
   Research 换 1 个 Coding（方案融合后单线串行，因为模块间耦合紧密）；
   高级分析则方案清晰后三路 Coding 并行。
2. **文档智能体永远最后出场**。数字（测试数/工具数/错误码数）在代码冻结后
   由实测脚本产出，再由文档智能体写入，杜绝"边写代码边写文档"的漂移。

## 5. 经验教训

### 5.1 陈旧 build 目录导致 wheel 遗漏新模块

**事故**：新增 `analysis/` 子包后重建 wheel，构建成功、时间戳新鲜，但包内
根本没有新模块——根因是残留的根级 `build/` 目录（上次构建的 build/lib
快照）让 `python -m build --wheel` 打包了旧文件集，而 `find_packages` 明明
正确发现了新包。

**沉淀的验证门**：新增任何子包后，重建前必须同时清理 `build/` 与 `dist/`，
重建后用 `python -m zipfile -l <wheel>` 列出归档内容核对新模块在列。
**构建成功退出码 + 新鲜时间戳 ≠ 新文件已打包**。

### 5.2 文档与代码数字漂移

**问题**：阶段 1/2 开发后 INSTALL_GUIDE.md 仍写着"408 passed、MCP 33 个
工具、readonly 22 个"，模块清单缺 memory/watchpoint.py 与 analysis/ 子包。

**机制化解决**："文档收尾任务"成为每轮迭代的固定末位任务，流程固定为：

1. 实测取数（`pytest --collect-only` 得测试总数；脚本枚举 MCP default /
   readonly 工具数）；
2. 逐处替换文档数字，全文 grep 旧数字确认无残留；
3. 数字一致性作为验收标准之一。

这条经验后来升级为项目级工程约束：**文档中的每个关键数字都必须可追溯到
一条可复现的实测命令**。

### 5.3 并行锚点冲突的预防话术

事后总结不如事前警告。现在的并行任务提示固定包含三要素模板：

1. **告知对方存在**："另一智能体正在并行修改同一文件的 X 区块"；
2. **划定只读边界**："你只允许在 Y 锚点追加，不得移动/重排/删除锚点外任何行"；
3. **隔离测试与验收**："新测试写入独立文件，最终验证需等并行方完成后重跑全量基线"。

配套判定规则（§3.5 案例一）：失败先归属再修复，报告者不等于责任人。

### 5.4 决策清单框架作为复盘工具

项目把全部架构选择整理为 **32 项决策、五个层次**（编号体系与 01/02 文档
一致），本次复盘即按此框架组织：

- **初始架构层 D1–D10**：CLI+MCP 双模式、JSON 信封、session 复用、稳定
  错误码、dry-run+confirm、反作弊拒绝边界、自动备份、FakeBackend、可选
  依赖降级、Windows 聚焦；
- **分析能力层 D11–D17**：confidence+evidence、UE 内省探测、邻近归组批读、
  三层缓存、异步任务、capstone 选型、r2pipe 桥接；
- **token 效率层 D18–D22**：name chain、宏系统、工具分组、会话快照、结果
  落盘分页；
- **安全增强层 D23–D27**：多级 profile、运行时档位、dry-run 状态、风险分级、
  DEFAULT_HINT；

框架的实用价值：**每项决策都能回答三问**——当时解决了什么痛点（§3.6 的
映射表）、备选方案是什么、为什么否决（计划文件 Rejected Alternatives 原文
可查）。复盘因此不是回忆录，而是可核对的审计。

## 6. 总结：多智能体协作的适用场景与边界

**适用**：

- 功能可分解为文件集不相交的并行分支（本项目 ③④⑦ 阶段均因此提速）；
- 存在明确、可自动化验证的基线（pytest 数字是最好的调度依据）；
- 方案取舍有争议、值得多视角对抗（三视角规划的 ROI 最高场景）。

**不适用 / 边界**：

- 模块间强耦合、总量适中的功能——UE 内省最终是单 Coding 智能体单线串行，
  并行只会制造冲突；
- 锚点无法清晰划定的枢纽文件热区——与其强行并行，不如排队串行；
- 没有测试基线保护的重构——追加式铁律失效时，多智能体放大的是破坏而非产出。

一句话收束：**多智能体协作的收益不来自"更多手"，而来自把计划、锚点、
基线、归属判定这些协调机制显式化**——人团队协作同理，只是 AI 把这套纪律
执行得更机械、更可复现。
